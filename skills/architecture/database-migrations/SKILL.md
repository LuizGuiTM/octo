# Database migrations

Migrations are hard to reverse and run against shared data. **Ask the user** before running any
migration against a non-local database.

## Rules
- One migration per logical change, generated by the project's tool (Prisma, Alembic, EF, Flyway…),
  never by editing an already-applied migration.
- Every migration is reversible, or its irreversibility is stated in the spec.
- Zero-downtime changes use expand → migrate → contract across deploys:
  1. Add the new column/table (nullable or with a default), and deploy code that writes both.
  2. Backfill in batches (bounded, resumable, idempotent).
  3. Switch reads, then drop the old column in a later release.
- Never rename or drop a column that deployed code still reads.
- Large tables: add indexes concurrently when the DB supports it; avoid long locks.
- Data migrations are separate from schema migrations and are tested with representative data.

## Plan tasks
Put the migration in the earliest wave (other tasks depend on it) and include:
- the up/down commands,
- a test that runs the migration on an empty DB and on a seeded one,
- the rollback step.

## Review checks
- [ ] Locks and runtime on production-sized tables were considered.
- [ ] Defaults and nullability match the domain rules.
- [ ] Foreign keys and indexes support the new queries.
- [ ] No PII copied into new places without need.
